Documentação para desenvolvedores

API do Lastro

A API recebe um diagrama de arquitetura e devolve, para um volume de acessos, a ocupação de cada componente, o tempo de resposta, o gargalo e quantas instâncias faltam. Este documento mostra como chamar cada rota e lista o que a API deve fazer.

  • Versão 0.1.0
  • Formato JSON (UTF-8)
  • Endereço local http://localhost:3333/api
  • Atualizado em 2 de novembro de 2026

Antes de começar

Toda rota fica sob /api. Em desenvolvimento, a API roda na porta 3333 (mude com a variável API_PORT) e o Vite encaminha /api para ela. Em produção, o Caddy serve o frontend e encaminha /api no mesmo domínio.

Envie o corpo como JSON, com o cabeçalho Content-Type: application/json. Todo erro volta no mesmo formato, descrito em Erros.

A API ainda não tem autenticação nem limite de requisições. Qualquer cliente pode chamar todas as rotas. Não exponha a API na internet antes de atender os requisitos SEG-001 e SEG-002.

Exemplo 
npm install
npm run dev:api        # só a API, em http://localhost:3333/api
curl http://localhost:3333/api/health

Uma visita é uma passagem de uma requisição de entrada por um componente. Se a API chama o banco em 40% das requisições, o banco recebe 0,4 visita por requisição de entrada.

Rotas

GET/api/health

Diz se o servidor está no ar. Use em monitoramento e na checagem do balanceador. Não recebe corpo.

Resposta 200
{ "status": "ok" }

POST/api/simulations

Simula um diagrama num volume de acessos. A resposta traz o resultado de cada componente, de cada ligação, do sistema inteiro e a curva do tempo de resposta. O cálculo é puro e síncrono: a mesma entrada sempre gera a mesma saída.

POST/api/waitlist/pro

Inscreve o visitante na lista de espera do Plano Pro e guarda qual recurso motivou o clique. A rota é provisória: as inscrições ficam na memória do processo e somem quando o servidor reinicia (veja API-013).

CampoTipoRegra
featuretextoDe 1 a 40 caracteres. O frontend envia header, cost ou scenarios.
Resposta 201
{ "subscribed": true }

Campos da resposta

Cada item de components

CampoO que é
reachableExiste caminho do ponto de entrada até o componente. Se for false, ele não recebe carga.
visits, syncVisitsVisitas por requisição de entrada. syncVisits conta só as que o usuário espera.
throughputRpsVazão no componente: tráfego de entrada × visitas.
serviceDemandMsVisitas × tempo de serviço, por requisição de entrada.
utilizationOcupação média por instância: vazão × tempo de serviço ÷ instâncias. Passa de 1 quando satura. Num banco com réplicas ou pool, é a maior das filas.
saturatedA fila cresce sem limite.
waitProbabilityChance de uma visita esperar na fila (Erlang C).
waitTimeMs, responseTimeMsEspera na fila e tempo total por visita. null se saturado.
statusok, warning (a partir de 75% do limite seguro) ou critical (no limite seguro ou acima).
instancesInstâncias consideradas. Com autoscaling, as ligadas nesse tráfego.
requiredInstances, additionalInstancesInstâncias para ficar abaixo do limite seguro e quantas faltam.
monthlyCost, extraMonthlyCostCusto mensal das instâncias e custo das que faltam.
maxEntryRps, safeEntryRpsTráfego de entrada que leva o componente a 100% e ao limite seguro. null se ilimitado.
database só bancoprimary e replicas (cada um com servidores, vazão, ocupação, tempo, situação e capacidades), limitedBy e primaryOverSafe.
autoscaling avançadominInstances, maxInstances, targetUtilization, activeInstances, atMax, requiredMaxInstances.
cache avançadohitRate, hitsRps, missesRps.
connectionPool avançadosize, extraHoldMs, inUse, utilization, saturated, status, waitTimeMs, maxEntryRps, requiredSize, limiting.
rateLimit avançadolimitRps, utilization, requiredLimitRps.

system

CampoO que é
bottleneckIdComponente que satura primeiro quando o tráfego cresce. null se nada no caminho tem limite.
maxCapacityRps, safeCapacityRpsTráfego de entrada que leva o gargalo a 100% e ao limite seguro.
saturatedAlgum componente alcançável está saturado.
responseTimeMsTempo de ponta a ponta no caminho síncrono: soma de visitas síncronas × tempo por visita.
hasBackgroundWork, backgroundDelayMsSe há ligações assíncronas com carga e quanto tempo o trabalho delas leva. Vale o ramo mais lento.
requestsInFlightRequisições em andamento, pela Lei de Little: tráfego × tempo de resposta.
monthlyCost, extraMonthlyCostSoma dos custos de todos os componentes.

links e curve

Cada ligação volta com throughputRps, as chamadas por segundo que passam por ela. A curve tem 50 pontos { trafficRps, responseTimeMs }, de 0 até 98% da capacidade máxima. Se a capacidade for ilimitada, a curva vai até o dobro do tráfego pedido.

Problemas de diagrama (details de um 422)

Cada problema traz code e message, e pode trazer componentIds (para destacar no editor) e linkIndex (posição da ligação em graph.links). A API junta todos os problemas numa resposta só. Alguns deles a validação de formato pega antes, com 400.

TOO_MANY_COMPONENTS, TOO_MANY_LINKSMais de 200 componentes ou 1.000 ligações.
INVALID_COMPONENT_ID, DUPLICATE_COMPONENT_IDComponente sem id ou com id repetido.
INVALID_COMPONENT_TYPETipo desconhecido.
INVALID_INSTANCESInstâncias fora de 1 a 10.000 ou não inteiras.
INVALID_SERVICE_TIMETempo de serviço fora da regra do tipo.

INVALID_CONNECTION_POOLPool sem conexão ou tempo extra negativo.
INVALID_RATE_LIMITLimite de chamadas 0 ou negativo.

Requisitos

Os requisitos seguem o apêndice “How to Write a Good Requirement” do NASA Systems Engineering Handbook. Cada um tem um identificador único, descreve uma só capacidade, pode ser verificado e diz por que existe.
